# 科技论文分享图文：persona 调研与发布格式

调研日期：2026-07-29。样本通过已登录的 OpenCLI 小红书只读搜索与笔记详情获得；互动数是页面查询时的快照，不代表因果效果，也不应被外推为平台通用算法规律。

## 样本观察

| 样本 | 快照互动 | 可复用结构 | 不应照搬的部分 |
|---|---:|---|---|
| 《深入解读 Kimi 爆火论文，马斯克都转了！》 | 3,689 赞 / 3,733 收藏 | 强兴趣钩子 + 明确论文对象 + 主题标签 | 外部名人背书或“爆火”等未由论文本身支撑的表达 |
| 《论文读不懂，先让 AI 这样拆》 | 1,419 赞 / 2,142 收藏 | 五步任务拆解；每步给可复制、可执行的提示；结尾承接评论 | 把论文解读退化为泛用工具清单，丢失论文证据 |
| 《确实，推荐系统已经彻底跨到 LLM 技术栈了。》 | 945 赞 / 975 收藏 / 52 评论 | 先给行业变化，再抛出三个读者问题，随后用作者的判断逐项回答 | 将个人现场经历、行业推断写成论文的已验证结论 |

## 对当前链路的结论

原有“核心贡献 → 创新 → 方法 → 结果 → 链接”是资料卡，适合存档，但不是唯一的阅读路径。高收藏样本更常见的价值是：让读者能快速判断是否要继续读、怎样把论文用于自己的问题，或如何核查结论。

因此 persona 不是语气皮肤，而是发布结构选择：

| persona | 正文路径 | 优先目标 | 适用论文 |
|---|---|---|---|
| `research_translator` | 结论 → 问题 → 方法 → 证据 → 启发 | 降低理解门槛 | 大多数单篇论文 |
| `implementation_reviewer` | 复现判断 → 模块 → 实验 → 缺口 | 收藏与工程使用 | 有代码、实验细节多 |
| `industry_analyst` | 行业问题 → 三问 → 论文回答 → 已验证证据 → 推断 | 评论讨论 | 技术路线变化明显 |
| `study_coach` | 问题 → 方法 → 证据 → 阅读行动 | 初学者收藏 | 概念或方法门槛高 |
| `evidence_auditor` | 主张 → 证据链 → 局限 → 复现边界 | 建立可信度 | 结果宣称强、需审慎解读 |
| `weekly_curator` | 选中理由 → 一句话 → 证据 → 适读人群 | 快速筛选 | 多论文周报或日更 |

## 强制约束

1. 每个正文都把论文、PDF 与 GitHub（或“暂无官方代码”）单独成段。
2. 未从摘要/解析文本确认的指标、代码、实验条件必须写“原文未披露”，不得用模型补全。
3. `industry_analyst` 的“可能影响”必须标为推断，不能冒充已部署事实。
4. 图文首页使用清晰论点；后续依次放架构、证据/结果、案例；最后再放知识图谱和论文详情。
5. 每个 persona 保留一个与其阅读任务一致的评论问题，而不是泛泛的“有问题评论区见”。
