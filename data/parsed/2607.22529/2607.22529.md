# Skill Self-Play: Pushing the Frontier of LLM Capability with Co-Evolving Skills

- **arXiv**: 2607.22529（2026-07-24，v1）
- **团队**: Qwen Large Model Application Team, Alibaba（联合 港中大 / 人大 / 中山 / 北大 / ETH 等）
- **代码**: https://github.com/Qwen-Applications/skill-self-play（Apache-2.0）

## 摘要（原文）
LLM 训练正从人工设计与标注转向交互驱动的自我演化。然而现有自演化方法在「任务多样性」与「验证可靠性」之间陷入两难：环境受限法（代码执行器、棋类模拟器）反馈精确，却把学习锁死在窄域；开放自生成覆盖广，却缺乏可靠验证，导致误导奖励污染训练回路。作者指出 **agent skills** 是调和这一张力的强力中间层——每个技能在特定场景保证深度、可验证的执行，而技能间的动态路由维持开放的任务多样性。据此提出 **Skill Self-Play (Skill-SP)**：由 Proposer、Solver、动态 Skill Controller 组成的共演化框架，经强化学习循环持续自博弈——Proposer 按动态采样技能生成挑战性任务，Solver 探索解以推高能力边界，Skill Controller 收集执行反馈更新与扩充技能库。实证显示 Skill-SP 持续抬高强骨干的性能天花板，并让初始错配模型实现惊天逆转。

## 动机：自演化的两难
- **环境受限法**：反馈可靠，但任务空间窄（出了棋盘学不到真实工具调用）。
- **开放自生成 + 事后过滤**：覆盖广，但易出矛盾题/伪难题/换皮题，过滤器只能删坏题、教不会出题器什么是好题，质量会塌缩。
- **技能库（Evolving Skill Library）** 作为中间件：把出题规则、示例与可执行验证器打包进 skill，给 Proposer 结构化先验。

## 方法：三方共演化
1. **Proposer（出题者）**：按动态采样技能生成任务 + 有效性校验 + 难度/效用估计；奖励 `R = 1{有效} × (1 − 2|预期成功率 − 0.5|)`，瞄准 Solver 约 50% 可解的「最近发展区」。
2. **Solver（答题者）**：只看题，探索候选解，推能力边界。
3. **Skill Controller（技能控制器）**：聚合成败与新颖样本，精炼、剪枝、归纳技能。
- 双层优化（bilevel）：内层训 Solver，外层同步优化 Proposer 与技能库。
- 关键设计：技能流（结构化）与开放探索流（无约束自由生成）混合，防止模型只「应试」自己能验证的题。

## 实验
- **任务**：工具调用（BFCL 多语言函数调用、API-Bank L1–L3）+ 逻辑推理（ZebraLogic 斑马谜题约束满足）。
- **骨干**：Qwen3-4B/8B、Ministral-3-8B/14B、Granite-4.1-3B（3B–14B）。
- **论文报告**：工具调用绝对提升最高 **+42.9**，逻辑推理 **+12.0**，一致优于无引导自博弈（Unguided SP）。
- **Qwen3-4B 工具调用 Overall**：Full System **66.7** vs Unguided SP **64.1**。
- **消融（Qwen3-4B）**：冻结技能库→64.4(−2.3)；冻结 Proposer→64.6(−2.1)；冻结 Solver→63.7(−3.0)；全冻结→63.5(−3.2)。三项缺一不可。
- **关键洞见**：只用技能流生成的数据会损害泛化，必须保留开放探索流。

## 局限
- 验证器过拟合风险：技能可能只在自身验证器内泛化，难迁移到任务套件之外。
- 对初始极弱模型仍需起跳点，极端难任务仍是天花板。
- 实验集中在可验证任务（工具调用、逻辑谜题），真实世界复杂度更高。

## 备注
- 技能仅用于训练；最终 Solver 推理时保持 prompt-only（不挂载技能库）。
- 技能演化仅占约 6.5% 墙钟时间，大头仍是 RL 滚动（源自官方 README）。
