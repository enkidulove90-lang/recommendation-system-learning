# OpticalRec 单篇直接上线设计规格

## 1. 范围与目标

本次只处理现有线上文章 `paper-2610.05432`，保留其 URL：

`https://enkidulove90-lang.github.io/article/paper-2610.05432/`

本次允许用新提示词重新生成这篇文章并更新同一个 Notion 页面与同一个 Hexo 源文件。不得批量重跑其他论文，不得重新执行 MinerU，不得改变其他文章的正文、URL 或分类。

## 2. 输入与模型调用

- 复用已经存在的 MinerU Markdown；目标文件长度低于现有 80,000 字符上限，因此完整内容进入 DeepSeek。
- 保留现有正文生成要求和系统提示词，不增加篇幅、章节内容、语气或结论方面的限制。
- 仅新增两类要求：
  1. 公式格式：行内公式使用 `$...$`，块级公式使用 `$$...$$`。
  2. 从确定性代码提供的候选 `ref_id` 中选择恰好两篇最相关参考文献，并为每篇给出简短理由。
- DeepSeek 不生成 DOI、arXiv URL、代码 URL，也不能选择候选集以外的编号。
- 正文与参考文献选择由同一次 DeepSeek 响应返回，但在缓存、校验和渲染层作为两个逻辑结果处理。

## 3. 候选提取、链接与降级

- 确定性代码从 MinerU 的 References 区域解析条目，稳定编号为 `ref_001`、`ref_002`……。
- 只有含 arXiv ID 或 DOI 的条目进入候选集；arXiv 版本后缀和 DOI 尾部标点必须规范化。
- 论文链接由 arXiv/Crossref 的确定性查询验证，不能采用模型生成的链接。
- 代码链接只允许来自固定版本、带 SHA256 校验的本地 Papers with Code 快照；快照不存在或无匹配时 `code_url=null`，不影响发布。
- 不使用 BM25。
- 当推荐子结果超时、JSON 无效、重复、越界、缺理由或链接不可用时，正文结果仍可继续；推荐部分按“年份降序 → arXiv YYMM 降序 → 原引用顺序”补足最新两篇，并标注为“补充阅读”。
- 如果一个模型选择有效、另一个无效，保留有效项并从确定性顺序补足；补足项不伪造“相关性理由”。
- 没有任何有效候选时，不渲染推荐区块。

## 4. 缓存与幂等

缓存键包含：

- 规范化 MinerU 正文哈希；计算时排除自动追加的推荐区块；
- 候选元数据哈希；
- DeepSeek 模型名；
- 正文提示词版本；
- 排序提示词/规则版本。

正文缓存和推荐缓存逻辑分离。正文与候选未变化时不得再次调用模型；正文命中而推荐缓存未命中时使用确定性降级，不为推荐单独调用模型。

推荐区块只允许位于文章末尾以下标记之间：

```text
<!-- related-reading:start -->
<!-- related-reading:end -->
```

重复执行必须替换同一区块，不能追加第二份。

## 5. 页面呈现

- 只对 `paper-2610.05432` 生效。
- 标题和各级标题使用黑体字族；中文正文使用宋体字族；数字和拉丁字母优先 Times New Roman。
- 数学公式由 MathJax 渲染；MathJax 只在目标文章路由加载。
- 推荐区块成功使用“延伸阅读”，确定性降级使用“补充阅读”。每项展示题名、年份、简短理由（若有）、论文链接和可选代码链接。

## 6. 发布与回滚

- 发布前保存目标 Notion 页面的 Markdown 快照、目标 Hexo 源文件、两者 SHA256 和当前 Git 提交。
- 写入只针对明确的 job ID、Notion page ID 和 slug `paper-2610.05432`；任一身份不匹配立即停止。
- 先 dry-run、再本地构建、再写 Notion、再提交单篇源文件与路由样式、最后等待 GitHub Pages 成功。
- 上线验收失败时，恢复 Notion 快照并回滚本次网站提交；不得触碰其他页面。

## 7. 测试与证据契约

每个测试用例必须在本地证据目录 `.paper-work/evidence/paper-2610.05432/<run_id>/` 产生唯一证据文件，并登记到 `manifest.json`。每条记录包含测试编号、命令、退出码、断言、证据路径和 SHA256。

只有同时满足以下条件才算通过：

1. 自动测试断言通过；
2. 对应证据文件存在且 SHA256 可复算；
3. 证据内容与断言一致；
4. 脱敏扫描中 `Authorization`、`Bearer`、token、password 和密钥模式零命中；
5. 所有强制测试编号均在 manifest 中恰好出现一次。

若测试通过但证据缺失或内容矛盾，整体仍判定失败；回到该测试所属设计任务调整方案、实现和测试，然后重新执行全部门禁，不允许带异常证据上线。
